# ESP32-S3 硬件接入（mix.ino）

协议依据 `esp32s3/mix/mix.ino` 与 `TransportRuntime.h`。浏览器只调用后端接口、显示后端 MJPEG 预览，不连接或采集本机摄像头和麦克风。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| `esp32s3/mix/TransportRuntime.h` | 固件通道选择、命令解析、发送队列及非阻塞输出 |
| `mcu/control.py` | 模式命令与固件确认契约 |
| `core/hardware_profile.py` | USB 连接默认波特率、固件端口、采样参数、包长度与帧率上限 |
| `core/config.py` | 环境变量覆盖部署连接参数 |
| `mcu/transport.py` | 串口字节流、TCP 字节流和独立 UDP 音频包；连接和资源清理 |
| `mcu/protocol.py` | COBS 分帧、固件兼容、长度检查及类型解码 |
| `mcu/client.py` | 接收调度、实时缓存、后端录制窗口和线程同步 |
| `services/media_service.py` | 会话视频导出；音频导出委托设备接口 |
| `services/hardware_service.py` | HTTP 路由使用的硬件操作、状态汇总和预览 |
| `features/detection/useHardwareSettings.js` | 前端连接配置与状态轮询 |

## 数据格式

所有数值采用小端格式。串口中所有数据、TCP 中温度/雷达/JPEG 均为 COBS 编码后追加 `00` 分隔符；UDP 音频直接发送原始包，没有 COBS 编码和分隔符。

| 数据 | 原始包 | 通道 |
| --- | --- | --- |
| 音频 | `01` + 256 个 int16，共 513 字节；48 kHz 单声道 | 串口、UDP |
| 温度 | `02` + float32 环境温度 + float32 物体温度，共 9 字节 | 串口、TCP |
| 雷达 | `04` + float32 BPM，共 5 字节 | 串口、TCP |
| 图像 | 完整 JPEG，以 `FF D8` 开始、`FF D9` 结束，没有额外类型头 | 串口、TCP |

温度和雷达约每 500 ms 发送一次。雷达为 LD6002 非接触设备，初始零值不是有效心率，且固件会重复发送缓存 BPM。固件未发送逐搏 RR 间隔，硬件 HRV 返回空值；分析中如有视频 HRV，保留视频结果，不从重复 BPM 构造 HRV。

摄像头为 VGA，JPEG 质量参数设为 10（ESP32 Camera 数值越小画质越高），采集间隔 100 ms，上限约 10 fps，实际受传输和队列影响。后端预览以 95 质量转码，减少二次压缩造成的画质损失。导出视频用后端接收时间估算平均帧率；没有固件时间戳，无法精确恢复每帧拍摄时间。沿用原工程的逆时针旋转 90° 加水平镜像作为安装方向校正，这不是固件 JPEG 格式要求。

情绪页语音图显示后端 PCM 的有符号采样滚动窗口；心率趋势只显示 LD6002 上报的 BPM 历史，不混入视频算法推算值。采集停止后页面再拉取一次硬件快照，使末尾样本留在图表中。

## 连接与录制

- 当前设备通过 ESP32-S3 USB 口连接，主机端波特率默认配置为 `2000000`；端口按后端主机实际设备配置。新固件的 USB `Serial.begin(2000000)` 与主机配置一致；雷达独立 UART 仍为 115200。
- WiFi：后端先监听 UDP `8889`，再连接 ESP32 当前 IP 的 TCP `8888`。ESP32 取 TCP 客户端 IP 作为 UDP 音频目标；后端只接收该 IP 的 513 字节音频包，源端口不作限制。
- 固件使用 DHCP；示例 IP 不保证等于设备实际地址。后端主机必须能接收设备发来的 UDP，容器/NAT 部署需保证路由和端口映射适配。
- 固件只允许一个 TCP 客户端，使用后端服务时不要同时连接独立采集脚本。
- 前端修改端口只修改后端配置，不会改变固件端口；自定义端口需要固件同步修改。环境变量见 `Emotion-Detect-py/.env.example`。
- 固件持续采集，仅在选中通道输出；模式切换命令与录制窗口独立。`/hardware/start` 清空并开启后端录制窗口，`/hardware/stop` 停止保存；实时预览仍可继续。
- 切换传输方式会结束录制并清除实时缓存；保留已录制会话供分析，下次开始时清空。断线时清除旧实时值，重连时丢弃旧半帧。

## 已知固件限制

旧版 `mix.ino` 的 COBS 编码器在原始包以零结尾时省略最终空块，标准解码会少一个尾零；新固件已修复为标准 COBS。后端仅在串口/TCP 解码后的已知定长包恰好少一字节时补零；UDP 不做补齐。此兼容方式不能区分恰好少一字节的损坏帧，固件也没有校验和。其余长度错误直接拒绝。过大的未完成帧丢弃至下一个分隔符，避免无限积累。

音频没有序号或时间戳，队列满时固件可能丢包，后端无法检测或补回丢失采样。当前使用 ESP32-S3 USB 连接，主机端配置为 2000000；实际 USB 吞吐与丢包情况需实机联调确认，不根据传统 UART 的波特率推断 USB 带宽。

## 验证

`tests/test_mix_firmware.py` 复现固件 COBS 编码器，验证尾零、分片、异常包、缓存恢复、雷达缺失 HRV、录制截止和录像计时；`tests/test_wifi_transport.py` 使用本机 TCP/UDP 验证双通道通信。测试不要求真实设备，也不代表已经验证板卡吞吐或传感器精度。

## 只有占位画面时

“WAITING FOR CAMERA FRAME”表示传输连接存在，但尚未解码到图像，不代表摄像头正常。检查 `/hardware/data` 的 `video.has_signal`，以及 WiFi `transport.tcp_bytes_received`、`udp_packets_received`、`last_error` 和 `local_ip`。TCP 收包数为零时优先检查设备当前 IP、单客户端占用和网络路由；VPN/TUN 可能先接受主机连接而尚未连通设备。连接到虚拟网卡不等于设备已就绪。

## 单通道输出与跨通道切换

上电默认 Serial 输出（不写入闪存）。WiFi 保持联网并监听 TCP 8888，USB 始终接收命令；没有采集输出的通道仍然可控制。后端每次建立目标连接（包括重连）立即发送 `MODE WIFI\n` 或 `MODE SERIAL\n`。因此 Serial → WiFi 时连入 WiFi 控制口即可切换，WiFi → Serial 时从 USB 发命令即可切换，不要求旧通道仍连通。

确认帧通过命令所在通道返回：原始 `10 01 01` 表示 Serial，`10 01 02` 表示 WiFi，采用 COBS + 零分隔符。`/hardware/mode` 返回的 `output_mode_status` 区分 pending、confirmed、unconfirmed；三秒内没有确认会提示检查新固件，不把仅修改后端配置当成设备已经切换。切换会丢弃旧代次的排队数据及半帧，以零分隔符恢复解析。数据流中已经发送到主机内核缓冲的字节无法撤回。

固件职责：`mix.ino` 初始化传感器、独立 I2S 采集任务以及温度/雷达/图像采集；`TransportRuntime.h` 管理模式与输出。USB 和 WiFi 分别由独立任务发送，主采集循环不再直接写 USB。WiFi TCP 每轮最多发 1460 字节，使用非阻塞 socket；同轮先处理控制命令和 UDP 音频，避免大图写入拖住其他数据。图像等待队列只保留最新一帧；VGA 10 fps 上限不变，JPEG quality 从 12 调到 16。后端 MJPEG 预览也限制为 10 fps，避免按约 30 fps 重复编码发送。短时拥塞可能丢帧/音频，不能保证所有网络环境下无卡顿。

部署时用 Arduino IDE 打开整个 `esp32s3/mix` 目录中的 `mix.ino`，确保同目录 `TransportRuntime.h` 一同参与编译，再烧录新固件；只替换网页不会生效。关闭占用 USB 的串口监视器/后端后再烧录，之后启动新版后端。在网页选择目标模式，等待“设备已确认”后检查画面、声音与传感器数据。USB 必须连接后端主机，WiFi 地址必须是设备 IP（当前 192.168.8.11）。

本次编译验证使用已安装的 ESP32 Arduino Core 3.3.11、ESP32-S3、Hardware CDC/JTAG、CDC On Boot Enabled、OPI PSRAM；实际烧录时 Flash/PSRAM 和 USB 模式须使用板卡原有有效配置。编译验证不等于已烧录或已测量实际端到端延迟。
